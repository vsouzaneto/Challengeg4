### Problem Definition

The requested outcome is working prioritization for sellers, with a manager view. The challenge describes opportunities prioritized by intuition, with sellers spending effort on deals unlikely to close. Business value is a more defensible allocation of seller attention, with expected revenue as the north star; the dataset cannot prove causal revenue uplift. Sellers need understandable priorities and actions; managers need portfolio filtering and temporary overrides. The immediate feature includes validated Engaging scoring and explicitly relative Prospecting priority. Authentication, CRM writeback, automated retraining and persistent overrides are excluded. Fixed real data, honest temporal evaluation, no paid runtime AI, and reproducible local execution constrain delivery.

Root problem: sellers cannot consistently identify which current opportunities deserve attention or explain that choice from available evidence.

## Phase 3: Requirements Analysis

### Functional Requirements Analysis

The approved requirements define five business capabilities: trustworthy input, stage-specific prioritization, faithful explanation/action, seller/manager operation and reproducible delivery. Their observable contracts are preserved below. Happy-path behavior must remain distinct from safe degradation; output absence is required when a probability cannot be validated.

### Functional Requirements

All approved Requirements remain authoritative: real four-table data; explicit recovery and validation; chronological leakage-safe evaluation; logistic/boosting comparison for full/fallback routes; calibrated Engaging ordering or labeled nonprobabilistic fallback; smoothed Prospecting backoff; actual-score explanations; deterministic playbook; two-tab role-aware screen; session-only manager pins; documented evidence and same-revision deployment.

### Non-Functional Requirements

Identical data/configuration produce identical scoring. Filter/navigation changes do not retrain. Every invalid row is reported or causes an explicit global failure. No runtime paid/generative AI calls. Local Python 3.11 environment with pinned dependencies reproduces results. No unsupported latency, model-accuracy target or dataset count is asserted.

### Constraints & Assumptions

Application implementation is limited to the three approved units. Changes remain under the submission. Model parameters and acceptance rules are documented before final-test examination. Browser checks validate actual rendering; passing import or HTTP checks alone do not establish usability. Existing user instructions prohibit gate bypasses.

### Measurable Outcomes

Exactly two stage views; all active rows accounted for; zero prohibited prediction fields; disjoint chronological periods; two candidate families times two feature routes; one common score absent; zero runtime generative calls; all selected test cases passing. Model metrics and data counts must be measured, not estimated from briefing approximations.

### User Scenarios

1. Primary: seller selects their identity, opens their own Engaging portfolio, compares validated priorities and inspects evidence plus a next action.
2. Alternative: seller opens Prospecting and sees relative priority, potential revenue, sample support and the reason for any backoff.
3. Alternative: manager starts with all sellers, filters to one seller and temporarily pins a deal with visible attribution.
4. Error: missing account selects fallback; an unsupported row stays visible with a correction; globally unusable data blocks scoring with diagnostics.
5. Degraded/session: failed probability validation suppresses probabilities; recalculate or start a new session clears temporary pins while a filter does not.

### Refined Description

Build a working lead-prioritization tool for sellers and managers using the four real CRM tables from Challenge 003. Help sellers decide which active opportunities deserve attention and understand why, with expected revenue per seller as the business north star. Keep Engaging and Prospecting separate because their historical outcome evidence supports different claims.

For Engaging, expose closing probabilities only when chronological evaluation supports their reliability, order by validated probability band, then use expected revenue within a band. Otherwise show explicitly relative priority with validation diagnostics. For Prospecting, show relative historical priority, evidence strength and potential product revenue. Every supported priority must have faithful plain-Portuguese factors and an evidence-grounded next action; unsupported deals remain visible with the missing condition named.

Provide seller-own and manager-team views, compact comparison rows, deal details and attributable temporary manager priority that expires on recalculation or a new session. Deliver reproducible execution, honest evaluation records and a verified live version of the validated revision. This is a static-data decision-support prototype, not authenticated CRM automation or evidence of causal revenue uplift.

Included: four-table data integrity, both stage priorities, full/fallback routes, explanation/action, role-filtered inspection, temporary overrides, reproducible tests/evidence and live verification. Excluded: authentication, separate services/frontend/database, CRM writeback, persistent overrides, paid/generative runtime AI, drift monitoring and scheduled retraining.

### User Scenarios Summary

## RRD Refinement — STAGE 8

One complete decomposition/filtering/reweighting cycle applied.

### Decomposition Check

| Dimension | Too broad? | Separates BAD/GOOD? | Action |
|---|---|---|---|
| Probability Evidence Traceability | No | Yes | Keep route-to-evidence linkage |
| Correction Specificity | No | Yes | Keep repairable field/condition specificity |
| Explanation Fidelity | No | Yes | Keep numeric reconstruction only |
| Ranking Test Discrimination | No | Yes | Keep ability to detect value-first ordering |
| Project Guidelines Alignment | No | Yes | Keep reproducible delivery identity as anchor |

A preliminary “overall code quality” candidate was dropped before rubric assembly because it would reward subjective style without a single observable contrast.

### Misalignment Filtering

No live model success is required; probability suppression is valid when justified. No extra service, authentication, load target or test dependency is rewarded. Illustrative example metrics are not acceptance targets. Fidelity is checked on the explained model scale rather than incorrectly forcing pre-calibration contributions to sum to calibrated probability.

### Redundancy Filtering

| Pair | Correlated? | Action |
|---|---|---|
| Probability traceability / Explanation fidelity | No: evaluation provenance can be correct while local contributions are false | Keep |
| Correction specificity / Explanation fidelity | No: unsupported-row diagnosis is distinct from supported-row model explanation | Keep |
| Ranking discrimination / Probability traceability | No: accurate validation evidence does not prove ordering tests catch defects | Keep |
| Guidelines alignment / Probability traceability | Partial: both require identity, but submission reproducibility spans the whole delivery | Limit guidelines to delivery provenance, retain 0.20 |
| Other dimension pairs | No material implication between scores | Keep |

### Weight Optimization

Initial uniform weights: 0.20 each. Task-risk adjustment: probability traceability +0.05, explanation fidelity +0.05, correction specificity -0.05, ranking discrimination -0.05, guidelines unchanged. No highly correlated pair remains after narrowing. Final weights: 0.25 + 0.15 + 0.25 + 0.15 + 0.20 = 1.00. Task-specific risk weighting is used instead of assigning speculative optional rubric dimensions merely to fill a category allocation.

# Description

> **Required Skill**: You MUST use and analyse `explainable-crm-prioritization` skill before doing any modification to task file or starting implementation of it!
>
> Skill location: `.claude/skills/explainable-crm-prioritization/SKILL.md`

Build a working lead-prioritization tool for sellers and managers using the four real CRM tables from Challenge 003. Help sellers decide which active opportunities deserve attention and understand why, with expected revenue per seller as the business north star. Keep Engaging and Prospecting separate because their historical outcome evidence supports different claims.

For Engaging, expose closing probabilities only when chronological evaluation supports their reliability, order by validated probability band, then use expected revenue within a band. Otherwise show explicitly relative priority with validation diagnostics. For Prospecting, show relative historical priority, evidence strength and potential product revenue. Every supported priority must have faithful plain-Portuguese factors and an evidence-grounded next action; unsupported deals remain visible with the missing condition named.

Provide seller-own and manager-team views, compact comparison rows, deal details and attributable temporary manager priority that expires on recalculation or a new session. Deliver reproducible execution, honest evaluation records and a verified live version of the validated revision. This is a static-data decision-support prototype, not authenticated CRM automation or evidence of causal revenue uplift.

**Scope**:

- Included: four-table data integrity, both stage priorities, full/fallback routes, explanations/actions, role-filtered inspection, temporary overrides, reproducible verification and live delivery evidence.
- Excluded: authentication, separate services/frontend/database, CRM writeback, persistent overrides, paid/generative runtime AI, drift monitoring and scheduled retraining.

**User Scenarios**:

1. **Primary**: A seller selects their identity, opens their own Engaging portfolio, compares priorities and inspects evidence plus a next action.
2. **Alternative**: A seller opens Prospecting and sees relative priority, potential revenue, sample support and the reason for backoff.
3. **Manager**: A manager starts with the team, filters to one seller and temporarily pins a deal with visible attribution.
4. **Data error**: Missing account data selects fallback; an unsupported deal stays visible with a correction; globally unusable data blocks scoring with diagnostics.
5. **Degraded/session**: Failed validation suppresses probabilities; recalculation or a new session clears pins, while filtering preserves them.
