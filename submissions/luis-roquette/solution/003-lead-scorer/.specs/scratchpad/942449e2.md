## Architecture Analysis

Greenfield three-module design is an approved future boundary, not an existing architectural pattern. Planned flow: versioned CSVs -> data.py validated rows/diagnostics/fingerprint -> scoring.py historical split and four trained/calibrated/evaluated routes plus Prospecting aggregates -> app.py role-filtered stage queues and row detail. The scoring result must distinguish calibrated probability, relative priority and insufficient data so the UI cannot fabricate missing probability. Manual priority belongs only to app.py session state. Recovery must be a separate explicit CLI entry in data.py or equivalent scoped support command, never an app startup side effect.

No existing function signatures can be reported. Proposed interface responsibilities and result fields are planning guidance, explicitly not verified symbols. No Repository/Factory/API-service pattern is justified.
