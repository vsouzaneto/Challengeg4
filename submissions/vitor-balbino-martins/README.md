# vitor-balbino-martins

> Generated by **py-manager** | Auth: `jwt` | DB: `postgres`

## Architecture

```
vitor-balbino-martins/
├── api/
│   └── v1/
│       ├── endpoints/       # HTTP handlers (thin, no business logic)
│       └── dependencies/    # FastAPI Depends (auth, pagination, db)
├── services/                # Business logic layer
├── repositories/            # Data access - Repository pattern
├── models/                  # SQLAlchemy ORM models
├── schemas/                 # Pydantic v2 DTOs (Create / Update / Response)
├── infrastructure/
│   ├── database/            # Engine, session, UnitOfWork, migrations
│   ├── security/            # JWT / API Key / OAuth2
│   ├── cache/               # Redis helpers + cache decorator
│   ├── events/              # In-process domain event bus
│   ├── tasks/               # Async background task helpers
│   └── http/                # httpx async clients (external APIs)
├── middlewares/             # Starlette middlewares (logging, error handling)
├── core/                    # Config, logger, exceptions, response models
├── tests/
│   ├── unit/
│   └── integration/
└── main.py                  # App factory + lifespan
```

## Flow per request

```
Request -> Middleware (log + error) -> Endpoint -> Service -> Repository -> DB
```

### Persistência do Dashboard e Kanban

O dashboard não precisa recalcular o RAG a cada abertura. A sincronização materializa
os dados nas tabelas `support_tickets` e `dashboard_snapshots`.

```bash
curl -X POST http://localhost:8000/api/v1/dashboard/sync \
  -H "Content-Type: application/json" \
  -d '{"dataset":"customer_support_tickets.csv","hourly_cost":50}'
```

Depois da sincronização, o frontend consulta `GET /api/v1/dashboard` para os KPIs e
`GET /api/v1/dashboard/tickets` para o Kanban. A movimentação persiste somente o
estado operacional (`new`, `triage`, `progress` ou `done`), preservando os dados
originais do CSV e suas referências de auditoria.

### Relatório de suporte

O endpoint `POST /api/v1/reports/support` executa dois agentes Ollama: extração de
problemas/categorias e consolidação operacional. As métricas são calculadas sobre o
Dataset 1 e incluem contagens por canal, prioridade e tipo, médias de resolução e as
combinações com maior tempo médio.

```json
{
  "dataset": "customer_support_tickets.csv",
  "sample_size": 20
}
```

## Frontend

Painel estático em HTML, CSS e JavaScript (ES modules), sem build e sem dependências
de runtime além da fonte Inter. **Toda tela consome a API** — não há dado de exemplo
embutido em lugar nenhum.

```
frontend/
├── index.html          # shell: navegação, as 5 views, diálogo de configuração
├── styles.css          # design tokens + componentes
└── js/
    ├── app.js          # boot, roteamento por hash, health check
    ├── api.js          # cliente HTTP, normalização de erro, timeout, cancelamento
    ├── config.js       # resolução da base URL, datasets, timeouts por endpoint
    ├── store.js        # estado compartilhado + cache do relatório
    ├── format.js       # formatadores pt-BR
    ├── dom.js          # helpers de DOM e blocos de estado
    ├── charts.js       # barras, divergentes, medidores, tabelas
    └── views/          # uma view por endpoint
```

### Como abrir

O frontend usa ES modules, então precisa ser servido por HTTP (abrir o arquivo
direto pelo `file://` não funciona).

```bash
# terminal 1 — backend
python manage.py run

# terminal 2 — frontend
python -m http.server 5500 --directory frontend
```

Acesse `http://localhost:5500`. O backend não serve arquivos estáticos: o frontend
roda em uma origem separada e fala com a API por CORS, que já vem liberado em
`CORS_ORIGINS`.

### Conexão com a API

A base URL é resolvida nesta ordem:

1. o valor salvo no diálogo **Configurar API** (`localStorage`);
2. `?api=` na query string, por exemplo `http://localhost:5500/?api=http://192.168.0.10:8000/api/v1`;
3. a mesma origem, quando a página é servida pela porta 8000;
4. `http://localhost:8000/api/v1`.

O indicador no rodapé da barra lateral consulta `GET /api/v1/health` e mostra três
estados: conectada, degradada (API no ar e banco fora) e fora de alcance. Clicar
nele abre a configuração.

As requisições vão **sem credenciais**. O backend responde
`Access-Control-Allow-Origin: *`, que o navegador recusa em requisições credenciadas;
para usar cookies seria preciso fixar `CORS_ORIGINS` em uma origem explícita.

### Telas

| Tela | Endpoint | O que mostra |
|------|----------|--------------|
| **Relatório** | `POST /reports/support` | KPIs, distribuições por canal/prioridade/tipo, nota por canal, correlações de Pearson, piores combinações, achados dos agentes e o bloco de auditoria com as fontes |
| **Agrupamentos** | `POST /clustering` | Tamanho de cada grupo e, por grupo, a distribuição de canal/prioridade/tipo e os tickets mais próximos do centroide |
| **Satisfação** | `POST /reports/satisfaction` | Nota média por tópico contra a média geral, os tópicos extremos e a tabela de evidências com a linha de origem no CSV |
| **Busca RAG** | `POST /rag/search`, `POST /rag/index`, `GET /rag/index/status` | Consulta semântica no PGVector e o painel de estado da indexação, com acompanhamento do progresso |
| **Custo** | derivada de `metrics.waste` | Custo do excedente sobre o benchmark; as horas vêm da API, o custo/hora e a fatia capturável são premissas do usuário, rotuladas como tais |

### Tempo de execução

Os endpoints têm custos muito diferentes, e a interface reflete isso:

- `POST /reports/support` lê o CSV inteiro e envia **um lote por vez ao Ollama**.
  Com 8.469 tickets e lotes de 500, são 17 chamadas ao modelo — pode levar vários
  minutos. Por isso a geração é uma ação explícita, com contador de tempo decorrido,
  botão de cancelar e o resultado guardado em `localStorage`, para não precisar
  rodar de novo a cada recarga. A view de Custo reaproveita esse mesmo resultado.
- `POST /clustering` e `POST /reports/satisfaction` são pesados de CPU mas não usam
  o Ollama; ambos têm limite de 20 minutos e podem ser cancelados.
- A navegação entre telas não interrompe nada: uma execução em andamento continua.

Configure `OLLAMA_BASE_URL` e `OLLAMA_MODEL` no `.env`. O Ollama deve estar em
execução com o modelo baixado (`ollama pull llama3.2`).

### Visualização

As decisões de codificação visual seguem um único princípio: a cor só carrega
informação que o comprimento da barra não carrega.

- **Categorias nominais** (canal, tipo, tópico, cluster) usam um único azul. Colorir
  cada barra por tamanho gastaria o canal de identidade repetindo o que o comprimento
  já mostra.
- **Categorias ordinais** (prioridade) usam uma rampa azul de 4 passos e saem na ordem
  natural, não por contagem, para a cor crescer junto com a posição na lista.
- **Polaridade** (nota acima ou abaixo da média) usa barra divergente com azul de um
  lado e vermelho do outro, sempre com o sinal escrito no valor — a cor nunca é a
  única pista.
- **Todo gráfico tem um gêmeo em tabela.** Nenhum valor existe apenas no hover.
- As barras respondem a mouse e a teclado (`Tab`), com o mesmo tooltip nos dois casos.

As cores dos gráficos foram validadas contra as duas superfícies reais do painel
(`#ffffff` e `#272729`): rampa monótona, distância de luminosidade ≥ 0,06 entre passos
e contraste da ponta clara ≥ 2:1 com o fundo.

### Acessibilidade

- Navegação completa por teclado, com link "pular para o conteúdo".
- Estados de carregamento e erro anunciados via `aria-live`.
- Medidores e barras expõem `role`/`aria-label` com o valor.
- Contraste de texto ≥ 4,5:1 em todas as superfícies.
- Conteúdo vindo da API entra no DOM sempre via `textContent`, nunca por `innerHTML`.
